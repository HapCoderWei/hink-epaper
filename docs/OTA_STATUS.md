# BLE OTA 状态与风险审计

审计日期：2026-09-05；OTA v2 真机进度更新：2026-09-15。旧版风险结论适用于已发布 B1 和 `v0.1.1-name`：**这些版本继承的 ATC OTA 不具备经过本项目验证的可靠能力，禁止使用 ATC 网页升级。** 当前工作区的 OTA v2 是不同且不兼容的新协议。

下一里程碑已经启动，完整分阶段计划见 [OTA v2 里程碑](MILESTONE_OTA_V2.md)。新的 M0 开发版已移除旧 ATC 危险命令，只允许向非启动暂存区上传并校验。2026-09-12 已完成测试价签的 BLE 上传、设备 CRC32、SWire 暂存区逐字节回读、启动区未改动、旧命令拒绝、擦除/接收阶段的 BLE 断连与物理断电恢复、正常三色刷新及待机功耗回归；M0 全部验收通过，但仍没有安装命令。

2026-09-13 已完成 M1-C 与 M1-D 往返：新协议使用两个不同确认字并绑定候选 CRC，安装逻辑从 RAM 先启用已验证候选，再退役当前槽。测试设备从 A/v2 切换到 B/v3，再从 B/v3 回到 A/v4；每次 BLE 重连身份与 SWire 回读一致，完整 Flash 安装前后都只有两个启动标记字节改变。M1 随后关闭并进入 M2。

当前结论：**OTA v2 M2 已可用于这个个人项目在稳定供电下的日常无线升级；正常升级过程不需要连接烧录器。** 真机已经验证安装时断电继续、候选连续启动失败自动回滚，以及回滚意图后断电继续。仍建议保留可用的 SWire 救援焊盘和备份，因为没有独立不可变 bootloader；M3 身份认证/签名尚未实现，附近兼容客户端理论上仍可提交固件，因此不适合开放到不可信环境或直接按商业产品标准放行。

2026-09-15 增加第二种 FPC-A002 / SSD1680 屏幕的独立固件身份 `0x2198`；原 HINK-E0213A162-FPC-A0 继续使用 `0x213A`。网页 OTA 要求先手动选择屏幕型号，并把选择结果与固件清单核对，不一致时禁用上传和安装；设备固件还会在 `BEGIN` 阶段再次核对自己的 Board ID。新屏驱动和 BLE 三色刷新已经真机验证，但 `0x2198` 的第一次 OTA 往返仍待单独执行，因此不能用原板型的 OTA 验收结果替代。

M2 真机结果（2026-09-13）：安装前把旧槽首 4 KiB 屏蔽启动标记后备份到 `0x40000`，并在 `0x3f000` 追加带 CRC 的安装、试运行、确认和回滚记录。候选运行 5 秒后确认健康；连续 3 次未确认时恢复旧槽。真机完成三项安装物理断电和一项故障回滚物理断电；最终从失败 B/v20 自动恢复到 A/v19，75 条日志全部有效、0 条损坏，双槽与备份均经 SWire 回读核对。按用户的个人项目范围决定，不再重复商业级双向对称矩阵。

## 当前 OTA v2 代码具有什么

- GATT OTA 服务 UUID `0x221f`，写特征 UUID `0x331f`；旧 ATC `0x00–0x07` 命令全部拒绝。
- 使用槽 A `0x00000–0x1efff` 和槽 B `0x20000–0x3efff`，每次只擦写 SDK 指定的非活动槽。
- 上传时保持候选槽启动字节为 `0xFF`，逐包读回，并完整复验传输 CRC、HINK 清单、板型、版本、Telink 头部/长度和原生 CRC。
- `ARM_INSTALL` 与 `INSTALL` 使用不同固定确认字并绑定候选 CRC；安装延迟约 300 ms，先写并读回候选启动标记，成功后才退役当前槽并复位。
- M2 状态回应还显示恢复状态、启动判定和日志有效/损坏条数；网页只有在清单有效、候选已验证且用户确认稳定供电/SWire 救援后才显示两步安装区。
- 网页要求显式选择目标屏幕，当前支持 `0x213A`（HINK A162）与 `0x2198`（FPC-A002 / SSD1680）；候选清单不匹配时，上传、授权和安装三处都会阻止继续。
- M2 自动健康确认和受限掉电回滚已经过精简真机故障矩阵验证；仍没有 BLE 配对、应用层身份认证或签名校验。

## 旧 ATC OTA 已确认的问题

以下结论来自对本仓库 `firmware/src/ota.c` 和 2026-09-05 在线 ATC 页面 JavaScript 的逐行对照，不是推测：

1. 固件 `case 7` 最终确认应检查命令载荷中的校验字节，却检查 `out_buffer[5]`、`out_buffer[6]`。该缓冲区不是这条最终命令的载荷。
2. `crc_out` 在擦除、缓存和写页命令中不断清零；只有 `case 6` 才会遍历整个暂存区计算所谓 CRC。
3. ATC 页面的普通 `sendFile()` 完成上传后直接调用最终写入，没有先调用 `case 6`、等待并核对设备端结果。
4. 页面所谓 CRC 只是 128 KiB 所有字节的 16 位累加和，固件也是简单累加，不是抗传输错误能力更强的 CRC/哈希。
5. ATC 页面 `sendPart()` 可能单次写约 240 个数据字节，而本固件 BLE RX FIFO 单项为 64 字节。虽然 ATT MTU 设为 250，但不能据此证明应用接收缓冲可以安全承载该包长；本项目传图工具因此限制为每包 30 字节。
6. 最终复制会先擦除当前启动区，没有双分区引导选择、提交标记或自动回滚。擦除/复制期间断电可能导致设备无法启动，只能通过 SWire 恢复。
7. BLE 安全级别为 `No_Security`，固定 magic word 不是认证。附近的兼容客户端可能访问 OTA 写接口。

因此，网页能连接 OTA 特征、文件小于 128 KiB、ATT 写入返回成功，都不能作为 OTA 成功或安全的证据。

## 当前禁止事项与使用边界

- 永远不要使用旧 ATC 页面的 `Send Firmware`、`final flash`，也不要向旧固件发送手工安装命令。
- 当前 OTA v2 只允许用于可重新连接 SWire 的测试价签；烧录器可以在正常使用和 OTA 时断开，但救援焊盘与备份必须保留可用。
- 虽然 M2 核心断电恢复已经通过，仍不建议在电池接触不稳或低电压环境主动升级；若候选损坏到无法执行最早期恢复代码，仍可能需要 SWire。
- 不根据“上传到 100%”判断已经升级；必须经过完整校验、两个安装操作，并在重连后核对版本和槽位。
- 当前固定确认字只防误操作，不防附近主动攻击；M3 完成前不要在不可信 BLE 环境对正式设备开放。

## 推荐的 OTA v2 路线

1. 使用仍可接 SWire 的独立测试价签开发，保留 B1 和原始 Flash 回退文件。
2. 修正最终命令的载荷校验，增加严格的长度、固件头、目标型号和暂存范围检查。
3. 网页将上传、设备端完整校验、用户确认最终提交、复制和重启拆成明确阶段；设备校验成功前绝不擦除启动区。
4. 将 OTA 分包限制在已验证的 FIFO 安全范围（初始采用与传图相同的 30 字节数据负载），增加序号、偏移和重试。
5. 用真正的 CRC32 或更强完整性校验；身份认证/签名验证单独设计，不能用 CRC 代替安全认证。
6. 尽可能设计可恢复的引导/提交状态。若现有 ROM/启动布局无法实现掉电安全回滚，文档必须明确剩余风险。
7. 先通过 SWire 安装 OTA v2；然后在测试价签上完成至少一次 `v2 → v2.1` BLE 升级、断电场景和 SWire 救援演练。
8. 通过回读、重启、BLE 名称、传图刷新、断开重连和待机电流回归后，才把 OTA 标为可用。

现有旧 OTA 入口可能通过针对缺陷的特殊引导客户端绕行，但这种方法需要利用未验证的内部缓冲状态，不作为组装价签的推荐方案。
