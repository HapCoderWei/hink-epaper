# HINK 原厂固件备份与逆向记录

更新日期：2026-09-13

## 1. 文档目的与边界

本文记录第二块 HINK 价签的原厂 Flash 备份、首轮静态逆向结果，以及与本项目 OTA v2 M2/v19 固件的初步对比。后续继续逆向时，应把“二进制直接证实”“结合源码可确认”和“尚待验证的推断”分开。

原厂完整 Flash 可能包含设备唯一 BLE 地址、射频参数、校准信息和厂商代码，**不得提交到公开仓库，也不得把原始读取文件直接用于写入实验**。所有后续处理都应复制出工作副本；下面两份原始读取文件只作为证据和恢复源保留。

## 2. 备份证据

连接与读取结果：

- 目标芯片：TLSR825x 兼容，Chip ID `0x5562`，Revision `0x02`。
- Flash JEDEC ID：`0x856013`。
- Flash 容量：524,288 字节（512 KiB）。
- 原厂固件启动标记：相对地址 `0x00008` 为 `KNLT`。
- Telink 头部声明的原厂镜像长度：39,152 字节（`0x98f0`）。
- 两次完整 Flash 读取逐字节一致。
- 两份读取的 SHA-256 均为 `035f078f222f66c441b1f22364e14d07d4033c00ba5733e88498dc7d71f57993`。

本机文件（由 Git 忽略，不上传）：

- `output/HINK_FACTORY_NEW_TAG_20260913/factory_full_read_1_0x00000_0x7ffff.bin`
- `output/HINK_FACTORY_NEW_TAG_20260913/factory_full_read_2_0x00000_0x7ffff.bin`
- `output/HINK_FACTORY_NEW_TAG_20260913/backup_manifest.txt`

第一次通过 SWire 接管芯片时，芯片寄存器可以读取，但 Flash JEDEC ID、UID 和内容均返回 `0x00`。同步给价签重新上电后成功接管 SWire，再向 Flash 发送非持久化的 `0xAB`（Release from Deep Power-Down）命令，JEDEC ID 和内容随即恢复正常。整个备份阶段没有执行擦除、编程或 Flash 状态寄存器写入。

## 3. 原厂 Flash 布局

按 4 KiB 扇区统计，原厂 Flash 中存在非 `0xFF` 数据的位置如下：

| 地址范围 | 已观察内容 | 当前判断 |
|---|---|---|
| `0x00000–0x098ef` | `KNLT` 启动镜像，共 39,152 字节 | 原厂主程序 |
| `0x1f000–0x1f04e` | 79 字节非 `0xFF`，主要为 `0x00` | 用途未知，必须继续保留 |
| `0x20000–0x3efff` | 全 `0xFF` | 原厂未使用，现作为 OTA 槽 B |
| `0x3f000–0x40fff` | 全 `0xFF` | 原厂未使用，现作为 M2 日志及首扇区备份 |
| `0x76000` 所在扇区 | 少量设备身份数据 | 含持久化 BLE 地址，不公开原始值 |
| `0x77000` 所在扇区 | 1 字节非 `0xFF` | 用途未知，可能属于 SDK/校准配置 |
| `0x78000` 所在扇区 | 原厂读取时全 `0xFF` | v19 首次启动后用于本项目设置结构 |
| `0x7f000` 所在扇区 | 8 字节非 `0xFF` | 高概率为芯片/RF 定制参数，尚未解码 |

这个布局进一步证明当前 OTA 分区选择合理：两个 124 KiB 启动槽和 `0x3f000–0x40fff` 恢复区域不会覆盖原厂设备身份及高地址参数。`0x1f000`、`0x77000` 和 `0x7f000` 在用途完全确认前不得复用。

## 4. 原厂镜像的初步逆向证据

### 4.1 Flash 深度休眠不是加密保护

TC32 反汇编直接观察到：

- 原厂启动早期在约 `0x000a2` 装载 `0xAB`，用于从 Flash 深度休眠中恢复。
- 原厂代码约 `0x009be`、`0x00c9e` 出现 `0xB9`（Deep Power-Down），约 `0x009e6`、`0x00cf4` 出现对应 `0xAB` 唤醒。
- 本项目 v19 也在约 `0x01dba`、`0x01e10` 出现同一组 `0xB9/0xAB` 低功耗流程，指令结构与原厂版本高度相似，只是链接地址发生偏移。

因此，备份时读到全零不是永久调试锁、加密或厂商防复制机制，而是 Telink SDK 低功耗路径留下的 Flash 运行状态。原厂在这里值得借鉴的做法，本项目已经通过同源 SDK 基本继承。未来更应改进的是备份工具：接管 SWire 后先只读检查 JEDEC ID，遇到 `0x000000` 时自动尝试 `0xAB`，再允许读取，避免生成“全零假备份”。

### 4.2 镜像明显更精简

| 对比项 | 原厂固件 | 本项目 v19 |
|---|---:|---:|
| Telink 头部镜像长度 | 39,152 字节 | 61,320 字节 |
| 启动槽占用率（124 KiB） | 约 30.8% | 约 48.3% |
| 启动槽剩余空间 | 约 87.8 KiB | 约 64.1 KiB |
| OTA 恢复能力 | 尚未从原厂镜像确认 | 双槽、安装日志、断电继续、失败回滚 |

v19 比原厂多 22,168 字节，主要合理来源是 OTA v2 M2 的清单校验、CRC、双槽切换、恢复日志和回滚代码，以及本项目继承的多屏驱动和辅助模块。当前仍有约 64.1 KiB 槽内余量，因此不是容量风险；但原厂的精简方式值得作为后续裁剪基准。

优先检查本项目中是否仍链接了与本板无关的其他尺寸屏幕驱动、字体、NFC、UART、I2C、旧设置字段或演示服务。裁剪必须以链接映射和功能回归为依据，不能为了追求与原厂相同体积而削弱 OTA 恢复能力。

### 4.3 字符串和功能不能过度解读

原厂镜像几乎没有可读的产品名、版本号或日志，只在 `0x096f3` 附近发现 `huawei.com`。目前没有完成交叉引用，不能据此断言存在联网、华为协议或云服务；TLSR8359 本身也没有 Wi-Fi。它可能只是广播数据、SDK 示例数据、测试向量或未使用常量。

目前也没有从原厂镜像中确认与本项目相同的 128 位 EPD 传图服务、OTA v2 协议或可靠回滚机制。二进制中“没有直接搜到字符串/UUID”不等于功能一定不存在，仍需还原 ATT 表和调用关系。

## 5. 与 v19 写入结果的对照

写入本项目正常版 `HINK_OTA_V2_M2D_V19.bin` 后，完成了一次 512 KiB 全 Flash 回读：

- v19 文件长度：61,320 字节。
- v19 SHA-256：`126b37fc516e76f103131e0595a36112ff828ded8f372021adb562d3f30bbe97`。
- 回读前 61,320 字节与 v19 逐字节一致。
- 相对原厂备份，变化只发生在 `0x00000–0x0ef87`；从 `0x0f000` 到 Flash 末尾全部保持一致。
- 槽 B、M2 日志区、M2 备份区、BLE 身份区和原厂未知高地址扇区均未被烧录覆盖。
- 软件复位后，BLE 报告当前槽 A、目标槽 B、固件版本 19，并声明安装及恢复日志能力有效。
- 用户随后通过网页工具成功发送图片，确认 BLE 传图及实体屏幕刷新正常。

写入后完整回读位于：

## 6. 当前值得借鉴的部分

### 已经借鉴或保留

1. **Flash 低功耗处理**：原厂和 v19 都包含标准 `0xB9/0xAB` 深度休眠/唤醒路径，不需要重复实现。
2. **设备数据与程序分离**：BLE 地址及芯片定制参数位于高地址扇区；本项目烧录和 OTA 均不覆盖这些区域。
3. **紧凑的板级实现**：原厂镜像只有约 38.2 KiB，可作为裁剪无关模块时的参考下限，但不能与包含 M2 恢复能力的 v19 简单等量比较。
4. **未知数据保守处理**：原厂在 `0x1f000`、`0x77000`、`0x7f000` 留有少量数据。当前最正确的“借鉴”是先保持原样，不凭猜测复用空间。

### 最值得继续挖掘

1. **原厂 EPD 初始化序列和 LUT**：定位 SPI 写命令函数、屏幕复位流程、BUSY 等待和波形表，与当前 `epd_bwr_213.c` 逐项比较。这是最可能改善刷新稳定性、温度适应或残影表现的方向。
2. **BLE ATT 表与广播策略**：还原服务、特征、广播间隔、连接参数和断开后的重广播行为，判断原厂是否有更简洁或更稳的连接状态机。
3. **低功耗入口条件**：区分普通 suspend、deep retention、Flash 深度休眠和 GPIO 配置，之后在备用价签上做同供电、同仪表的功耗对照。
4. **高地址参数用途**：追踪代码对 `0x1f000`、`0x76000`、`0x77000`、`0x7f000` 的读取交叉引用，确认哪些是 BLE 身份、RF 校准、晶振参数或业务状态。
5. **代码体积构成**：生成 v19 链接映射，按 OTA、BLE、EPD、字体和遗留模块统计大小，优先删除确实未使用的内容。

## 7. 后续逆向工作规范

1. 校验两份原始备份哈希后，只分析复制出的工作副本。
2. 先用 Telink SDK 函数指纹剔除公共库代码，再命名厂商自有函数。
3. 每个结论记录二进制偏移、调用者、访问地址和置信度，不只记录反编译伪代码。
4. 屏幕 LUT、Flash 写入和低功耗改动只在可由 SWire 恢复的备用价签上实验。
5. 原厂镜像、BLE 地址和校准数据不上传公开仓库；公开文档只保留脱敏后的偏移、哈希与结论。
6. 当前 v19 已可日常使用，逆向实验应另开分支和诊断版本，不能直接覆盖正常发布固件。
