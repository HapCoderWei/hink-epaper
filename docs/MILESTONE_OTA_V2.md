# OTA v2 里程碑与分阶段方案

建立日期：2026-09-12。目标是在不牺牲现有显示、BLE 传图和约 42 µA 待机基线的前提下，为 HINK TLSR8359 价签增加可验证、可逐步放行的无线固件升级能力。

## 总原则

1. 每个阶段都必须可以单独编译、测试和真机验收，上一阶段没有通过就不加入下一阶段的破坏性能力。
2. 第一版只能写非启动暂存区，不能覆盖当前固件。先证明 BLE 分包、Flash 擦写、读回和 CRC32 链路可靠。
3. 保留 SWire 作为开发期救援入口；组装好的唯一设备最后放行。
4. 完整性、断电恢复和身份认证是三件不同的事。CRC32 只解决意外传输错误，不代表固件可信，也不能实现断电回滚。
5. OTA 网页只识别本项目的新协议。旧 ATC 命令不兼容，也不提供兼容开关。

## Flash 规划

| 区域 | 地址 | 当前用途 |
|---|---:|---|
| 启动固件 | `0x00000–0x1ffff` | 当前可启动应用；M0 完全禁止写入 |
| OTA v2 暂存镜像 | `0x20000–0x3efff` | 最大 124 KiB；M0 按镜像实际长度擦写 |
| OTA 元数据预留 | `0x3f000–0x3ffff` | 为后续清单、提交状态或恢复日志保留；M0 不写 |
| BLE MAC | `0x76000` 附近 | SDK 持久化设备地址；OTA 不碰 |
| 应用设置 | `0x78100` 所在扇区 | 现有设置；OTA 不碰 |

当前 M0 固件为 58,736 字节，能够放入暂存区。

## M0：只上传与校验，不安装

状态：**M0 已于 2026-09-12 全部通过。** SWire 安装、BLE 暂存上传、设备 CRC32、暂存区独立回读、启动区隔离、旧命令拒绝、擦除/接收阶段的 BLE 断连与物理断电恢复、正常三色刷新及待机功耗均已真机验证。

能力：

- 网页与设备先用 `INFO` 握手；旧固件不会解锁固件选择按钮。
- `BEGIN` 检查协议版本、板型 `0x213a`、镜像长度和预期 CRC32。
- 浏览器逐条发送 `ERASE_NEXT`；设备只能顺序擦除暂存镜像所需扇区。
- `DATA` 带 32 位顺序偏移，数据最多 24 字节且不能跨越 256 字节页边界。
- 每次写入后立即从 Flash 读回比较，成功后才更新接收位置和 CRC32。
- `FINISH` 只有在长度完整且设备 CRC32 与浏览器一致时进入 `VERIFIED`。
- 没有安装、复制或重启命令；旧 ATC `0x00–0x07` 命令均被拒绝。

M0 真机验收：

1. [x] 通过 SWire 给一块仍可救援的测试价签写入 `HINK_OTA_V2_M0.bin`，写后读回比对。
2. [x] 确认 BLE 名称、正常图像特征和固件内置测试图三色全屏刷新没有回归。
3. [x] 断开烧录器、关闭网页后测得稳定电流约 30–40 µA，间隔数秒出现约 0.2 mA 的 BLE 广播脉冲；与 B1 的约 42 µA 表读数基线一致。
4. [x] 网页选择同一固件执行“上传到暂存区并校验”，设备 CRC32 与浏览器一致。
5. [x] 用 SWire 读取暂存区实际镜像并与上传文件逐字节比较；同时复核启动区没有变化。
6. [x] 分别在擦除一半和上传 480 字节时主动断开蓝牙；两次均可重新连接，接收阶段进度保持正确，且启动区逐字节未变。
7. [x] 分别在擦除 1/2 扇区和接收 480/8192 字节的边界切断目标板电源；重新上电后固件正常广播，图像服务存在，OTA 会话回到 `IDLE`。
8. [x] 向 OTA 特征发送旧 ATC 最终写入命令 `0x07`；设备返回未知命令，且启动区保持不变。

## M1：最简安装，仅限可救援测试价签

进入条件：M0 全部真机验收通过。

状态：**方案已冻结；M1-A 至 M1-D 的 A→B→A 往返安装已于 2026-09-13 完成。** 设备依次从 A/v2 切换到 B/v3，再回到 A/v4；两次 BLE 重连身份与 SWire 双槽回读一致，每次安装都只有两个预定启动字节变化。当前只等待 v4 三色显示确认与待机功耗回归，之后可关闭 M1 并进入 M2 断电恢复。详细交接和执行顺序见 [M1 双启动槽实施方案](MILESTONE_OTA_V2_M1.md)。

M1 不再采用“暂存后复制覆盖 `0x00000`”的原计划。经 Telink 官方 B85 SDK 交叉确认，改用 `0x00000` 与 `0x20000` 两个 124 KiB 多启动槽：上传期间屏蔽候选槽启动标记，完整校验和两步确认后才写入新标记并清除旧标记。旧槽内容不擦除，SWire 始终作为救援入口。

M1 同时加入 HINK 固件清单、动态非活动槽保护、完整 Flash 复读、Telink 头部/长度/原生 CRC 校验、版本与槽位回报，以及网页明确的外部 3.3 V 确认。由于本 PCB 没有已确认的 VCC ADC 通路，PB7 又是屏幕 BUSY，M1 不实现虚假的设备端电压门限。

这一阶段仍只允许在稳定外部 3.3 V、SWire 可救援的测试价签上运行，不直接对已封装设备开放，也不把固定确认字称为安全认证。

## M2：断电恢复

进入条件：M1 已完成 A→B 与 B→A 往返升级，并用 SWire 证明两个槽和启动标记符合预期。

状态：**M2-A 至 M2-C 的源码、主机故障模型、TC32 编译，以及 M2-D 的看门狗/软件断点真机验证已于 2026-09-13 完成。** 当前设备运行 B/v10，A/v12 已退役；恢复日志 40 条有效、0 条损坏，备份与双槽回读一致。主机测试覆盖 A→B、B→A 安装与回滚中 16,944 个逐字节写入截断点，以及备份/恢复扇区擦除中断；真机已验证 v8 自动故障回滚、v10 安装意图断点恢复和 v12 回滚意图断点恢复。剩余工作是按矩阵执行安装/回滚窗口的物理断电；首次物理断电前必须单独等待人工确认。详细设计和证据见 [M2 断电恢复实施方案](MILESTONE_OTA_V2_M2.md)。

M2 在 M1 双启动槽基础上补齐正式恢复语义：

1. 用故障注入和物理断电分别验证目标标记写入前、写入中、写入后以及旧标记清除前后的实际启动选择。
2. 在预留元数据扇区设计带 CRC 的“试运行/已确认/回滚”记录，新固件必须完成启动自检并显式确认健康。
3. 验证新固件无法启动、无法广播或未在期限内确认时，是否能由最小恢复路径重新启用旧槽；若芯片启动机制无法可靠实现，必须保留 SWire 救援限制。
4. 明确旧槽何时可以擦除，以及断电后每一步是重试、回滚还是保持旧版本。

在上述故障矩阵通过前，即使 M1 往返安装成功，也不能宣称具备无人值守的掉电回滚。

## M3：身份认证和发布控制

进入条件：断电模型明确，安装链路经过重复验证。

计划增加：

- 至少加入每台设备的升级授权秘密或挑战响应，避免任意附近客户端提交固件。
- 优先评估签名清单，让设备只接受项目发布密钥签名的固件。
- 版本单调检查、防误刷硬件型号、升级历史和失败原因显示。
- 网页只在兼容浏览器、足够电量和正确设备型号下启用正式“安装并重启”。

## M4：组装价签放行

放行前必须同时满足：

- 连续多次 `旧版本 → 新版本` 真机升级成功。
- 上传中断、校验失败、重复分包、错序分包均不影响当前固件。
- 安装阶段断电的行为与文档一致；若承诺恢复，恢复测试必须通过。
- 升级后 BLE 传图、三色刷新、重新连接和待机电流全部回归。
- SWire 救援镜像、烧录步骤和版本文件已归档。

## M0 协议摘要

GATT 服务继续使用 `0x221f`，特征使用 `0x331f`，但命令语义与旧 ATC 页面完全不同。所有多字节整数均为小端。

| 命令 | 值 | 请求内容 |
|---|---:|---|
| `INFO` | `0x10` | 无 |
| `BEGIN` | `0x11` | 协议 1B、板型 2B、长度 4B、CRC32 4B |
| `ERASE_NEXT` | `0x12` | 无；每次只擦除下一个暂存扇区 |
| `DATA` | `0x13` | 偏移 4B、数据 1–24B |
| `FINISH` | `0x14` | 无；比较长度和 CRC32 |
| `STATUS` | `0x15` | 无 |
| `ABORT` | `0x16` | 无；只清会话状态，不擦启动区 |

设备每条命令通知 20 字节状态：标识、协议、回显命令、结果码、阶段、已擦/总扇区、最大分包、已收长度、镜像长度、当前 CRC32。

## 2026-09-12 真机记录

- 烧录器：TLSRPGM（TLSR8269，固件 `0.0.0.8`），串口速率 1,500,000 bit/s。
- 目标识别：TLSR825x ID `0x5562`、修订 `0x02`；TLSR8359 按 TLSR825x 兼容路径操作。
- Flash：JEDEC ID `0x856013`，容量 512 KiB。
- 烧录前对启动区前 60 KiB 连续读取两次，二进制完全一致；备份 SHA-256 为 `995e9eed39749bae8bcc0510d43f53142fe27620299ca249e509821e13464d12`。
- 写入地址：`0x00000`；写入长度 58,736 字节。写入仅擦除镜像覆盖的扇区，没有整片擦除。
- 初版真机握手暴露出首条 OTA 通知与 BLE 连接参数更新争用发送队列的问题；固件已改为先处理命令并排队回应，再申请高速连接。网页同时增加一次只读 `INFO` 安全重试。
- 连续擦除命令暴露出通知早于浏览器 GATT 写 Promise 完成的竞争；网页现同时等待“写操作完成”和“通知返回”，再发送下一条命令。
- 修正版写后读取 `0x00000–0x0e56f`，与 `HINK_OTA_V2_M0.bin` 逐字节一致；SHA-256 为 `82aed62a5a3037d5131e52d4e5c548cc4c84a6963ab08e84971bc2d05aed4933`。
- 网页向 `0x20000` 上传 58,736 字节并逐包读回成功，浏览器与设备 CRC32 均为 `C9990182`。
- SWire 直接读取 `0x20000–0x2e56f`，与源固件逐字节一致，SHA-256 同为 `82aed62a5a3037d5131e52d4e5c548cc4c84a6963ab08e84971bc2d05aed4933`。
- OTA 后再次读取活动区 `0x00000–0x0e56f`，与当前运行固件逐字节一致，证明本次 M0 没有修改启动区。
- BLE 真机脚本验证旧 ATC 最终命令 `0x07` 返回状态 9（未知命令）。
- 擦除完成 1/2 扇区时主动断开 BLE，重新连接成功；重新开始后写入 480 字节时再次断开，重新连接后设备报告 `RECEIVING` 且接收位置仍为 480，随后 `ABORT` 安全清除会话。
- 中断测试后再次读取活动区 `0x00000–0x0e56f`，与当前固件逐字节一致，SHA-256 仍为 `82aed62a5a3037d5131e52d4e5c548cc4c84a6963ab08e84971bc2d05aed4933`。
- 擦除 1/2 扇区和接收 480/8192 字节时分别断开目标板电源；两次恢复供电后均能直接连接，OTA 会话均为 `IDLE`，正常图像特征仍存在。
- 物理断电测试后通过正常图像特征发送内置测试图命令 `0x05`，价签完成黑/白/红全屏刷新，用户确认显示正常。
- 所有故障测试及屏幕刷新完成后再次读取活动区，仍与 `HINK_OTA_V2_M0.bin` 逐字节一致，SHA-256 未变。
- 功耗回归：3.0 V 供电，上电瞬态峰值约 3–4 mA，随后迅速降至 0.03–0.04 mA；间隔数秒可见约 0.2 mA 的短广播峰值。现有万用表无法积分脉冲平均值，但稳定读数未高于 B1 的约 0.042 mA 基线。
- macOS CoreBluetooth 在刚断开后可能暂时不把价签列入扫描结果，但已知 CoreBluetooth UUID 可以直接连接。真机脚本因此使用已知 UUID 并带有限次数退避重试，避免把系统扫描抖动误判为固件失联。
- 工具时序：硬复位 50 ms、激活 5,000 ms、激活后保持 CPU Stop。不要额外使用 `CPU Stall`；实测 Stall 状态会令 Flash JEDEC ID 和 Flash 数据读取异常。
- 备份、写入及读回日志保存在工作目录的 `output/HINK_OTA_V2_M0_20260912/` 中，不提交到公开仓库。

本地编译产物位于忽略目录，不会随源码提交。M0 只用于证明暂存链路和故障隔离，不提供安装能力；M1 才会在可由 SWire 救援的测试价签上加入最简安装流程。
